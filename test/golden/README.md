# Synthetic NRPT v1 golden fixture (cross-implementation)

`synthetic-2page.nrpt` (232 bytes, SHA-256
`eacb108ff1f88f4d2c3b7de5b37e2f5f3a9f4764ec9a2425e11326b5f59c0e70`) is a **synthetic**
NRPT v1 profile generated by the reference encoder
`NootedRedTool/Sources/NootedRedTool/ProfileCodec.swift`
(`ProfileCodec.encode`) from this model:

| Page | pageFileOffset | pageHash | matchFlags | Sites |
| --- | --- | --- | --- | --- |
| 0 | `0xE000` | `0xE18DB215D6994568` | `0x0007` (default v1) | `0x0081`: `c7477804000000` → `c7477801000000` |
| 1 | `0x1000` | `0x1111222233334444` | `0x0006` (hash + sites) | `0x0160`: `83e0fe` → `83c801`; `0x0200`: `750b` → `eb0b` |

Header: build `24H232`, APU mask `0x28` (Renoir | Green Sardine), device ID `0`, header flags `0`.

It contains **no Apple bytes**. Its two purposes:

1. **Cross-implementation parity** (`docs/PatchProfile-Spec.md` §16.9): the independent Python
   validator (`test/nrpt_validator.py`) must decode it to the model above and re-encode it to the
   **byte-identical** profile. The Swift reference codec and the Python codec were verified to
   produce byte-identical output for this model.
2. A stable golden input that cannot be rewritten by test code.

Regenerate (requires the Swift toolchain and a clean `ProfileCodec.swift`):

```sh
cat > /tmp/main.swift <<'SWIFT'
// ... build the model above and call ProfileCodec.encode(model) ...
SWIFT
swiftc -O NootedRedTool/Sources/NootedRedTool/ProfileCodec.swift /tmp/main.swift -o /tmp/codec-golden
/tmp/codec-golden   # writes the golden bytes
```

The golden profile is intentionally not a real 24H232 profile: real profiles are generated by the
task-7 generator from clean Apple binaries and are validated by `test/run-validation.sh` against the
host fixture; they are not committed.
